# cost · 性能算账

把性能数字换算成人话：**严重性、必要性、成本**。常用于 `/turbo` 优化完成后，或任何拿到性能数据想判断轻重缓急的时候。

## 何时使用

- 用户给出单次耗时 / 基准数字，问"这有多严重"
- `/turbo` 优化完成后，想量化收益
- 有性能目标（如响应 200ms），想对比差距
- 需要判断"该不该现在优化"

## 输入（缺什么先问）

- **必填**：单次耗时（基线或优化后）、数据规模。
- **影响面**：调用频率（QPS）或每日调用量 —— 问用户，或从调用点推断。
- **目标**：性能预算 / SLA（可选）。
- 缺失影响面时：用保守区间估算并**标注"估算"**；结论严重依赖该数字时，先问用户。

## 严重性分级

| 级别 | 判定 | 示例 |
|---|---|---|
| 🔴 严重 | 热路径（每个请求都跑）× 明显超预算（>10 倍目标） | 接口主链路 2s，目标 200ms |
| 🟠 中等 | 高频但未报警；或低频但超时严重 | 后台批处理 5s，每天只跑一次 |
| 🟢 轻微 | 一次性 / 离线任务，慢一点无感知 | 迁移脚本 30s，一个月跑一次 |

## 成本换算（把耗时变成人话）

- **每秒 CPU 占用** = 单次耗时 × QPS。例：200ms × 100 QPS = 每秒 20 秒 CPU → 需要约 20 核才跟得上。
- **每日浪费** = 单次耗时 × 每日调用量。例：1s × 200 万次 = 每天约 555 小时 CPU。
- **可感知程度** = 单次耗时 / 目标耗时。>10× 用户明确觉得"卡"；3–10× 偶尔卡；<3× 一般无感。
- **收益换算**：优化前后同口径各算一次，说"每天省 X 小时 CPU / 从 N 核降到 1 核"。

## 必要性结论

- **必须现在优化**：🔴 严重 + 可感知 + 改动小。
- **建议优化**：收益明显（>10×）且改动小。
- **可缓**：🟢 轻微 / 离线任务 —— 明确告诉用户可缓，**不要为了优化而优化**。

## 输出格式

数字 + 表格 + 一句结论。示例：

```
## 💰 算账

| 项目 | 数值 |
|---|---|
| 单次耗时 | 2.0s（目标 200ms，超 10×） |
| 调用频率 | 100 QPS（估算） |
| 每秒 CPU 占用 | 200 秒 → 需 ~20 核 |
| 可感知 | 🔴 用户明确觉得"卡" |

**结论**：必须现在优化。改为 set 查找后预计 ~20ms，每日省 ~550 小时 CPU。
```

## 红线

- 数字只来自实测；估算必须标注"估算"并给区间，**不编造精确数字**。
- 没有频率数据时，宁可用区间，不硬凑。
- 算账只提供判断依据，不替用户做决定。
