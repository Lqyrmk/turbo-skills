# turbo · 性能优化 + 可读注释

优化代码运行效率，同时保证优化后的代码可读、注释讲得清"为什么快"。

## 核心原则

1. **测量驱动**。没有基线数据的优化是猜。先测、再改、改完再测。
2. **只动热点**。最小改动换最大收益。顺手"优化"别处是禁术。
3. **可读性优先**。90% 的代码保持朴素；优化带来的复杂度必须用注释补回。
4. **可验证**。每次优化要么有数据证明更快，要么回退。

## 何时使用

- 用户要求优化性能、让代码跑得更快、降低延迟、解决卡顿/慢查询
- 处理大数据量或高并发的代码段明显低效
- 已有的慢代码需要优化

**何时不要用**：没有性能问题的证据时，不要主动优化（防止过早优化）。

## 工作流

按顺序执行，不要跳步。

### 1. 明确性能目标
先搞清楚（问用户或从代码推断）：
- 慢在哪：CPU 密集 / I/O 密集 / 内存 / 网络？
- 有没有量化指标：响应时间阈值、吞吐量、数据规模？
- 用户可感知的改进是什么？

### 2. 建立基线（Measure）
- 在待优化代码的**同一目录**下创建 `benchmark/` 文件夹，把基准脚本放进去（规则见下方「benchmark 组织」）。
- 运行基准脚本，记录优化前的关键数字：耗时、内存、调用次数。
- **没有基线就停在这里**：向用户说明无法测量，不做优化。

### 3. 定位瓶颈（Identify）
- 先看算法复杂度（O(n²) vs O(n)）和数据结构是否匹配数据访问模式。
- 再看循环内的重复工作、被频繁执行的 I/O、重复的分配。
- 语言有 profile 工具就用，找出真正热点，不靠猜。

### 4. 最小修复（Fix）
- 只改瓶颈所在，改动范围尽量小。
- 优先选"对结果影响最小"的手法（见下方目录）。
- 一次只做一项优化，便于归因。

### 5. 验证正确性（Verify）
- 行为必须完全一致：同样的输入 → 同样的输出。
- 跑现有测试；没有就加一条简单断言。
- 覆盖边界：空输入、大输入、异常输入。

### 6. 复测对比
- 用第 2 步**同一个** bench 脚本重测；若新增了场景，在 `benchmark/` 下补对应 bench 文件。
- 汇报：改动前 → 改动后 → 提升百分比。
- **提升 <1% 或不可测量的优化直接回退。**

### 7. 补注释
- 对被优化过、不再"一眼可读"的代码，按下方注释规范补注释。
- 保持朴素的代码不加注释（保持干净）。

### 8. 汇报
- 按下方「输出格式」汇报：**先一句话介绍被优化代码的功能，再给表格**。
- 数字必须来自第 2/6 步的实测，并给出注释和 benchmark 的位置。

## benchmark 组织

基准测试统一放在待优化代码的**同一目录**下的 `benchmark/` 文件夹里，不随手丢单文件。

    <代码目录>/benchmark/
    ├── bench.py        # 一个优化点 / 一个场景时
    ├── bench_1.py      # 多个优化点 / 多场景时，一个文件测一个场景
    ├── bench_2.py
    └── README.md       # 记录各场景的基线 / 优化后数字（推荐）

规则：

- **一个场景一个文件**。只测一处 → `bench.py`；优化点/场景多 → `bench_1.py`、`bench_2.py`…（也可按场景命名，如 `bench_lookup.py`）。
- **基准脚本独立可运行**：导入待优化的目标函数并计时。基准和优化后**共用同一个脚本**，复测才是同口径对比。
- 基准必须**可复现**：固定数据规模和种子，数字能重跑一致。
- 把基线/优化后数字写进 `benchmark/README.md`，用户不用重跑也能看到前后对比。

## 优化手法目录（语言无关）

| 手法 | 适用场景 | 收益 |
|---|---|---|
| 换数据结构 | 频繁查找：list → set/hash/dict | 高 |
| 降低复杂度 | 嵌套循环 → 单循环；排序后二分 | 高 |
| 缓存 / 记忆化 | 相同输入反复计算 | 高 |
| 批处理 | 单条 I/O → 批量（DB、网络、文件） | 高 |
| 移出循环 | 循环内不变的属性访问、函数调用、计算 | 中 |
| 惰性求值 | 结果用不到时不计算、不加载 | 中 |
| 资源复用 | 连接池、对象池、避免重复分配 | 中 |
| 减少复制 | 避免不必要的深拷贝、循环内字符串拼接 | 中 |
| 预分配容量 | 大小已知的容器 | 低–中 |
| 短路求值 | 高代价表达式放条件判断之后 | 低 |

**通用规则**：优先选高收益项；同类效果选改动最小的；一次只做一项。

## 可读注释规范

优化过的代码，注释必须明确标出三段，用固定标签开头。**三个标签都要出现，缺一段就不算合格**：

    # What:    这段代码在干什么（一句话讲意图，别复述代码本身）
    # Why:     为什么这样写更快 —— 对比朴素写法，讲清利用了哪个性质 / 复杂度降了多少
    # Revisit: 什么条件下这个优化失效，需要回退成朴素写法

示例（伪代码）：

    # What: 建 id → item 的哈希索引，供后续 O(1) 查询
    # Why:  dict 查找是 O(1)，避免循环内对 list 的 O(n) 线性扫描，整体从 O(n²) 降到 O(n)
    # Revisit: 若数据量很小（<100），线性扫描可能更快，可回退为朴素写法
    def build_index(ids, items):
        by_id = {it["id"]: it for it in items}
        return [by_id[i] for i in ids if i in by_id]

**写作要求（说人话，杜绝术语堆砌）**：

- 用大白话讲清"为什么快"。不说"利用哈希降低摊销复杂度"，说"用 dict 代替 list，查找从挨个比对变成一次命中"。
- 每段一句话，先结论后解释，主句尽量 20 字以内。
- What 讲意图，不重复代码。`# What: 找出重复项` 好过 `# What: 遍历列表检查是否在 seen 中`。
- 三段都很短时，可合并成一行、用 `|` 分隔，但**标签必须保留**：
  `# What: 建索引 | Why: list 的 in 是 O(n)，dict 是 O(1) | Revisit: 数据量小可回退`

### 什么时候必须注释，什么时候不要
- **必须注释**：任何"按朴素写法大家会怎么写、而你写得不一样"的地方；为了性能而命名的晦涩变量。
- **不要注释**：自解释的代码（`i += 1`）、函数名意图已清楚的地方、以及本身就很朴素、不需要优化的代码。

## 反模式（红线）

以下情况直接拒绝，除非有硬性的性能指标压着：

1. **过早优化**：没有测量证据就优化。
2. **微优化**：收益 <1% 或不可测量的优化（改名、循环展开、一次乘法的写法）。
3. **用可读性换性能**：可读性明显下降但提升 <10%，或提升无法量化。
4. **改行为换速度**：为快而改变语义/正确性（浮点精度、边界行为、错误处理）。
5. **顺手优化**：优化用户没指出的地方。

## 输出格式

每次调用结束，按下面的模板汇报。**先一句话介绍被优化代码的功能，再给表格**——让用户先知道这段代码是干嘛的，再讲怎么优化。

```
## ⚡ 优化汇报

**这段代码在做什么**：一句话讲清被优化代码片段的用途，例如「从物品列表里找出每个 id 对应的记录」。

| 项目 | 详情 |
|---|---|
| 🎯 瓶颈 | … |
| 🔧 改动 | … |
| 📊 结果 | 200ms → 40ms（快 5×） |
| ✅ 行为 | 不变 / 有说明 |
| 📝 注释 | 已补，见 `xxx.py:12` |
| 📁 基准 | `benchmark/bench.py` |

**备注**（可选）：行为变化说明、取舍提醒等。
```

**写作要求**：

- 数字必须来自第 2/6 步的实际测量，**不许编造**。
- 结果栏用「X → Y（快 N× / -Z%）」，突出可感知的提升。
- 注释位置具体到「文件:行」，基准给文件路径，方便用户自己重跑。
- 行为有变化时，必须写进「✅ 行为」栏，并在备注里说明。
- 整体控制在几秒能读完的篇幅。
